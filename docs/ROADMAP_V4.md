# Дорожная карта до v4: дизайн, вёрстка, оптимизация, производительность, безопасность

Составлена 2026-09-26 по коду `main` (после #371). Опирается на
`docs/ROADMAP.md` (второй релиз), `docs/PERFORMANCE_PLAN.md`, `SECURITY.md`,
`PRE_RELEASE_TASKS.md` и отчёт бюджетов качества. Цифры в разделе 0 сняты с
дерева, а не оценены; всё, что помечено «цель», — предложение, которое
проверяется замером.

## Принципы, которые не меняются до v4

- **Shared-хостинг и голый PHP 8.4+.** Никаких runtime-зависимостей Composer,
  никакой обязательной Node, Redis или очереди вне cron. Всё новое обязано
  работать на cPanel; Redis/S3 — только опциональные адаптеры, как сейчас.
- **Сначала замер, потом правка.** Каждая оптимизация получает «было/стало»;
  отказ по замеру — законный итог (как `content-visibility` в 2.4 плана скорости).
- **Храповик вместо кампаний.** Всякая величина долга переводится в бюджет
  `quality_budgets()` и дальше может только уменьшаться. Этот план в основном
  описывает, до каких значений опускаются потолки к каждой версии.
- **Один PR — одна обратимая правка**, через ветку и CI, как сейчас.
- **Осознанно не делаем**: SPA и клиентский роутинг, `@layer`, JS-плавную
  прокрутку, CSS-фреймворк, смену языка/фреймворка бэкенда, перевод админки.

## 2. Дизайн

Цель к v4: **одна дизайн-система на токенах**, где новый блок собирается из
готовых примитивов, а `!important` и «магические» числа не нужны.

### v3.0 — дизайн-система 2.0
- **Токены высоты (elevation).** 156 разных `box-shadow` → 4–6 уровней
  `--shadow-1…--shadow-5` + `--card-shadow`. Бюджет «разных box-shadow в теме»
  опускать ступенями 156 → 131 (✅ неразличимые варианты) → 101 (✅ ступени `--shadow-rest…lift-xl`) → 60 → 12.
- **Радиусы.** 32 разных → шкала `--radius-xs…--radius-xl` + `--radius-pill`;
  90 → 82 → 46 (✅ кнопки, поля, бейджи, панели; `--radius-xs/lg`) жёстких `border-radius` в публичном CSS → 0 (бюджет уже есть).
- **`!important`.** Главный источник — борьба специфичности темы с базой
  (`frontend.css` ↔ `gov-theme.css`). Лечится не удалением по одному, а
  переносом правил темы на `:where()`-селекторы с низкой специфичностью и
  слиянием дублирующих правил базы. Потолки: публичный 366 → 120 (v3.0) → 30 (v4).
- **Цвет секций и тёмная тема** — довести до полного покрытия токенами
  `--section-*`: ни одного цвета в правилах частей темы без переменной.
  Сторож т. 274 расширить на все части темы, а не только вынесенные.
- **Живой каталог компонентов** в админке (раздел «Дизайн» → «Компоненты»):
  все блоки с демо-данными (`BlockSamples`) в светлой/тёмной теме и при
  текущем акценте. Это же страница для визуальных регрессов вместо набора
  разрозненных фикстур.
- Контраст ≥ 4,5:1 при **любом** акценте из админки — уже считается
  `AccentContrast`; распространить проверку на цвета секций и кнопки обложки.

### v3.x — админка
- Влить 7 CSS-слоёв-патчей и `admin-media-loader.js` в основную сборку
  админки; `!important` админки 372 → 100. Новый бюджет «файлов-патчей админки» = 0.
- Единый набор компонентов формы (поле, группа, переключатель, образец цвета,
  выбор медиа) из `AdminUi` — формы блоков перестают верстаться руками.

### v4.0
- Темы оформления как пакет токенов (экспорт/импорт JSON из «Дизайна»),
  чтобы переносить облик между сайтами без правки CSS.
- `!important` публичный ≤ 30, тени ≤ 12 токенов, радиусы ≤ 6 — фиксация
  бюджетов «по факту».

## 5. Производительность

Цели v4 — **по реальным посетителям (RUM, p75)**, а не по лабораторному
Lighthouse: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1; TTFB HTML из кэша ≤ 200 мс.
Сбор уже есть (`WebVitals`, `/_vitals`) — не хватает только данных с прода.

### v2.x — базовая линия (без неё дальше не идём)
- Снять на боевом `asdr.uz` протокол из раздела 6 `PERFORMANCE_PLAN.md`:
  Lighthouse ×3 по главной/новости/странице/каталогу, WebPageTest, RUM за 2 недели.
- Серверный чек-лист: OPcache (+ `preload.php`), brotli/gzip, HTTP/2 или 3,
  `Cache-Control` ассетов — подтверждённые ответом сервера, а не конфигом.
- `php scripts/optimize_images.php` по всей медиатеке на проде (картинки,
  залитые по FTP или сидером, идут оригиналом — прямая потеря LCP) и cron для
  регулярного прогона.

### v3.0 — CSS
- **Разрез бандла до конца** (2.1 плана скорости стоит на паузе): общий
  критичный слой ≤ 25 КБ brotli (шапка, подвал, типографика, сетка,
  токены) + части по типам блоков через `AssetCollector::THEME_PART_MAP`.
  Неиспользуемый CSS на главной 318 КБ → ≤ 80 КБ raw. Бюджет
  `public.min.css` опускается вслед за каждой вынесенной частью.
- Снятие `!important` и слияние дублей (раздел 2) даёт второй выигрыш —
  дешевле пересчёт стилей, что важно для INP на слабых Android.

### v3.x — медиа и сторонний контент
- **AVIF** третьим `<source>` в `Media::picture()` и в `ImageBatchOptimizer`

- **Facade для YouTube везде**: блок «Текст», `SocialEmbed` в теле новости,

## 6. Безопасность

База сильная (аудит 07.09: 0 критичных). Дальше — **уровень 3**: убрать
оставшиеся осознанные послабления и сделать компрометацию дорогой и заметной.

### v2.x — до открытия публике
- Закрыть `PRE_RELEASE_TASKS.md`: `APP_ENV=production`, HTTPS + HSTS,
  служебные URL → 403/404, эталон целостности, внешние бэкапы с реальным
  восстановлением, SPF/DKIM/DMARC, внешний мониторинг `/health`.
- **Персональные данные**: решение по размещению — закон РУз «О персональных
  данных» требует хранить ПДн граждан Узбекистана на территории страны; для
  приёмной (v3.0) это обязательное условие выбора хостинга.
- `/.well-known/security.txt` с контактом для сообщений об уязвимостях.

### v3.0 — вместе с приёмной
- Приёмная — самая чувствительная часть системы: шифрование полей обращения
  в БД (`SecretBox`), отдельная роль доступа к обращениям, журнал каждого
  просмотра обращения, сроки хранения и автоудаление ПДн, антиспам без
  внешних сервисов (капча уже есть) и лимиты на номер/IP.
- OneID (my.gov.uz) — через OAuth-поток на cURL, токены только на сервере.

### v3.x — ужесточение
- **CSP без `style-src 'unsafe-inline'`**: стилевые атрибуты из кода → классы
  и переменные (раздел 3), динамические значения — в `<style nonce>`;
  `HtmlSanitizer` не пропускает `style` в контенте редакторов. Сначала
  `Content-Security-Policy-Report-Only` + эндпоинт отчётов с rate-limit,
  затем боевая политика.
- **Trusted Types** в админке (`require-trusted-types-for 'script'`) — после
  аудита `innerHTML` в `admin.js`.
- **Passkeys/WebAuthn — правильно**: проверка challenge, origin, подписи
  (ES256/RS256 через `openssl_verify`, без библиотек), счётчика; как третий
  канал второго фактора, затем как беспарольный вход.
- Пароли: Argon2id при доступности (`password_needs_rehash` — прозрачная
  перехешовка при входе), bcrypt — запасной вариант.
- 2FA обязательна для всех ролей, а не только для настроивших.

### v4.0 — обнаружение и восстановление
- Журнал действий с хеш-цепочкой (каждая запись подписывает предыдущую) и
  ежедневной выгрузкой хеша вне сервера — подмена журнала становится видна.
- Ротация ключа `SecretBox` с перешифровкой воркером; ключи вне веб-корня
  и вне бэкапа БД.
- Шифрование бэкапов (libsodium) до отправки во внешнее хранилище.
- Внешний пентест перед v4 и после каждой крупной фичи; CI-проверки
  расширить SAST-правилами под свои грабли (интерполяция в SQL, `echo` без
  `e()`, `json_encode` без флагов — часть уже стоит бюджетами).
- Сценарий реакции на инцидент (`SECURITY.md`) — учения раз в полгода, как
  репетиция восстановления.
